# 4.1 Workflow

**Core platform**

- **FR-01** (US-01) The app must be served only on the tailnet hostname through `tailscale serve`; the public reverse proxy must forward only the ingest path (FR-26).
- **FR-02** (US-01) Sign-in must accept a passkey, or a password hashed with argon2id plus a 6-digit TOTP code, with lockout per BR-29.
- **FR-03** (US-01) Sessions must use an HttpOnly, Secure, SameSite=Lax cookie lasting 30 days, listed and revocable per device in Settings.
- **FR-04** (US-02) The system must issue 10 single-use recovery codes, shown once and stored hashed; regenerating must invalidate the previous set.
- **FR-05** (US-02) A server command must clear all sessions and second factors, print a sign-in link valid for 15 minutes and write an audit entry.
- **FR-06** (US-03) Tokens must follow BR-28, be stored as hashes, and record a last-used time at most once a minute.
- **FR-07** (US-04) Each module must declare its id, name, icon, routes, nav entries, palette actions, token scopes, migrations, jobs and settings in one manifest, and a disabled module must register none of them.
- **FR-08** (US-04) The command palette must search module names, pages and keywords, open the result on Enter, and list recent items when the query is empty.
- **FR-09** (US-05) A nightly job at 02:00 server time (BR-34) must dump the database and snapshot `/srv/fiscus/data` with restic to B2, keeping 7 daily, 4 weekly and 12 monthly snapshots, and record time, size, snapshot id and status.
- **FR-10** (US-05) An hourly check must send an alert email when no backup succeeded in the past 26 hours, at most once per 24 hours until one succeeds.
- **FR-11** (US-05) A monthly job must restore the latest snapshot into a scratch database, compare row counts per table with production, and show the result on the System page.
- **FR-12** (US-06) A full export must produce one ZIP with CSV and JSON per module plus a manifest of row counts; only one export may run at a time, and the file expires after 24 hours.
- **FR-13** (US-01 to US-06) The audit log must record sign-ins, failed sign-ins, token creation, revocation and use, imports, rollbacks, trash, purge and settings changes, with before and after values for settings. A token's use is recorded once per day, on its first call that day. *Restated 15 Oct 2026: it did not say how often use is recorded.*
- **FR-14** (US-01) Fiscus must serve its web app at `/` on the tailnet hostname, with its own shell, navigation and start page. Below 1024 px it shows its phone layout, used in the phone's browser and only while online; there is no PWA (Q-08). The settings show the platform screens: sessions, API tokens, the System page, backups and the full export.

**Ledger and budgets**

- **FR-15** (US-07) Import must parse the 8-column Money Manager TSV with a selectable date format (default MM/DD/YYYY, A-12) and show a preview, including the first 10 parsed dates, before any write.
- **FR-16** (US-07) Commit must save all rows in one database transaction as one batch, skip flagged duplicates by default, and allow rollback per BR-27, which moves the batch's rows to Trashed.
- **FR-17** (US-07) Install must seed the 9 accounts and the Money Manager category list, plus budget items Makan, Kos, Investasi and Alokasi darurat (locked), Jajan, Laundry, Obat & Kesehatan, Belanja barang-barang and Transportasi (flexible), and Lain-lain as the catch-all; the owner enters all amounts.
- **FR-18** (US-08) Quick entry must put the amount first, default account and category to the last used, save in one tap and offer Undo for 5 seconds.
- **FR-19** (US-20, US-21) The phone app must queue each change made on it as a mutation with a client UUIDv7, send the queue in order through `sync/push` (FR-39), and use each mutation's id as its idempotency key. The web app queues nothing (Q-08). *Restated 12 Oct 2026: it was the PWA's offline quick-entry queue.*
- **FR-20** (US-09) A transfer must be one record with a source and a destination account.
- **FR-21** (US-10) New transactions must start Confirmed when created by the owner, the private API or an import, and Unreviewed when created by the ingest endpoint or a recurring rule (lifecycle in 4.3).
- **FR-22** (US-10) Every edit must append the previous values to the transaction's history.
- **FR-23** (US-10) Review must list Unreviewed transactions oldest first with their source, and offer confirm, edit, trash, confirm all, and "Trash all from this token since a date".
- **FR-24** (US-11) The private API must offer create, list (filter by cycle, account, category, status and text; at most 200 per page), get, update, trash, restore, budget status and afford check.
- **FR-25** (US-11, US-12) Every create call must require an `Idempotency-Key` handled per BR-09.
- **FR-26** (US-12) The public endpoint must accept only `POST /ingest/v1/transactions` with a `fiscus:ingest` token, enforce BR-30 and BR-31, and return ids only.
- **FR-27** (US-13) Budget figures must be computed per BR-10 to BR-18 on each view; closed cycles use their configuration snapshot.
- **FR-28** (US-14) The afford check must follow BR-19 to BR-22 in the UI and the private API; a KETAT result must list the 3 flexible items with the most budget left.
- **FR-29** (US-15) Settings edits must apply per BR-23, and closing a cycle must store its configuration snapshot.
- **FR-30** (US-15) Holidays must be kept per year and editable, seeded from your budgeting skill's list (A-13).
- **FR-31** (US-16) Categorisation rules must be applied per BR-32.
- **FR-32** (US-17) Recurring rules must run when a cycle opens, per BR-33.
- **FR-33** (US-18) Reports must show spending per budget item for the last 6 closed cycles, the top 10 notes by amount, and spending outside any budget item.

**Phone app**

The native Flutter app of Phase 3 ([ADR-0002](../architecture/decisions/0002-offline-first-mobile-app.md)). The first builds are Android only (Q-06).

- **FR-34** (US-19) The web app must show a one-time pairing code as a QR code (BR-37). The phone app must exchange it for a token named after the phone, with `fiscus:read`, `fiscus:write` and `fiscus:settings`, and keep the token in the phone's secure store. The token follows BR-28 and is listed and revoked in Settings › Tokens like any other. On a 401 the phone app stops syncing and asks to be paired again, keeping its queue.
- **FR-35** (US-20) The phone app must keep a full copy of the `fiscus` data in an encrypted SQLite database: all of it on the first sync, then the changes since its cursor (FR-40).
- **FR-36** (US-20) Without a connection, the phone app must serve every read from its copy. It must apply creates, edits, trashes, restores and confirms (Confirm all included) of transactions, accounts, categories, tags, templates, budget items and rules on the phone at once, marked "Waiting to sync". Payday, buffers, income, holidays, currencies and their rates, and "Trash all from this token since a date" need a connection. Imports, the export, tokens, Empty trash and the System page open in the web app (2.2).
- **FR-37** (US-20) Before a change is queued, the phone app must check the field rules (BR-01 to BR-08) and flag possible duplicates (BR-07) in Dart. It must also work out pay cycles (BR-10, BR-11, BR-13) for its period headers, and the base-currency value of amounts in other currencies (A-11, BR-18) for its totals and balances. These rules pass the same shared test cases as the server's (Q-01).
- **FR-38** (US-20) Quick entry in the phone app must follow FR-18 offline and online, and log each save's time, which is sent with the next sync (1.2).
- **FR-39** (US-21) `POST /api/v1/fiscus/sync/push` must apply its mutations in order (BR-35), each through the same service and rules as its REST endpoint (BR-38). It answers each one with applied and the new version, conflict and the server's row, or rejected and a violation code. A create whose id already exists answers applied, so a retry saves nothing twice, even after the key's 24 hours (EC-02).
- **FR-40** (US-21) `GET /api/v1/fiscus/sync/pull` must return every synced row changed since the cursor and below the watermark of the oldest running database transaction, in pages of about 1,000 rows, with the tombstones of purged rows. The response is versioned and only ever gains fields. A cursor older than the tombstones kept gets `410 cursor_expired` (BR-36).
- **FR-41** (US-21) A rejected mutation, and every queued mutation that depends on it, must wait in "Couldn't sync" with the reason, Edit and Discard (EC-25).
- **FR-42** (US-22) On a conflict, the phone app must pull, merge field by field against the row as it was before its edit, and send again the fields only it changed. A field both sides changed shows "Changed elsewhere. Review both versions." (EC-04). An edit to a transaction trashed elsewhere offers Restore and apply, or Discard (EC-24).
- **FR-43** (US-23, Should) Budget and the afford check on the phone must compute their figures from its copy per BR-10 to BR-22, in Dart, and pass the same shared test cases as the server. Until then they call the private API and need a connection.
- **FR-44** (US-24, Should) The phone app must offer a lock that asks for the phone's fingerprint, face or PIN before it shows any data.
